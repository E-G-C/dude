# Idea: Automatic Unchanged-Intent Redefinition

## Idea

The user wants as few interactions as possible during explicit autonomous Work, with more learning and more attempts that use materially different approaches. Automatic redefinition is a possible continuation route when implementation gets stuck. The user has deliberately asked to brainstorm this idea while putting Feature 013 aside.

The wanted capability is not permission for the loop to rewrite what the user wants. It is to let autonomous Work repair or evolve derived definition artifacts when the user-owned intent remains unchanged, so a defect in a plan or task decomposition does not require a human round-trip merely to say, "yes, repair the decomposition."

This idea begins only where trying another materially different implementation approach is insufficient because the plan or decomposition itself is defective. Runtime-approved autonomous recovery already exists and remains separate. Bounded revision autonomy is deliberately not part of this idea.

The smallest likely initial surface is the plan and canonical task decomposition. Whether `spec.md` may ever be corrected without changing user intent is intentionally unresolved, as are the evidence threshold, reconciliation rules, continuation behavior, and termination rule.

## Open Questions

1. Which derived artifacts may autonomous Work redefine while user intent is byte-unchanged: only `plan.md` and `tasks.md`, or may `spec.md` also be corrected without changing that intent?
   Answer: Allow automatic changes to `plan.md` and `tasks.md`. Permit `spec.md` correction only when outcome-equivalent: clarify a contradiction, relocate or replace an accidental execution constraint, or add a verified execution assumption that does not change the promised output. No normative outcome, acceptance, safety, quality, scope, or meaning-of-done obligation may be weakened or narrowed. The route may change; the promised outcome may not.
2. What deterministic evidence must prove that redefinition is necessary rather than another implementation approach still being available?
   Answer: Require either (a) a deterministic contradiction or impossible gate causally traced to the definition, or (b) Feature 009 learning governance evidence that materially different implementation approaches cannot resolve the same blocker. Do not force pointless retries when the contradiction is already provable.
3. How must the system prove that a proposed redefinition does not weaken requirements, acceptance criteria, safety constraints, quality bars, or the meaning of done?
   Answer: Map every pre-change outcome, acceptance, quality, safety, and failure obligation to an equal-or-stronger post-change obligation; keep the user-owned sections byte-identical; retain each acceptance check or replace it with a check that proves the same intended invariant. Independent semantic review remains mandatory because natural-language equivalence cannot be proven completely by deterministic code.
4. For the governance branch that triggered redefinition, must the pre-redefinition failing condition remain binding and evaluable even if later work adopts the corrected definition?
   Answer: The intended invariant and user outcome remain binding, but a proven-defective literal condition does not. Preserve the triggering evidence and replace the invalid condition with a reviewed check proving the intended invariant; do not keep a known-invalid gate merely because it existed before redefinition.
5. What structural validation must protect append-only coordinator logs, managed fences, canonical ownership, task-history preservation, and atomic rollback, given that existing lint missed the observed mid-entry corruption?
   Answer: Parse and validate structure rather than using textual anchors: require one balanced managed region, exact append-only log-prefix preservation, exact ownership, preserved task history, a guarded atomic batch, post-write reparsing, and all-or-restored rollback if any invariant fails.
6. How should task reconciliation work when redefinition splits, merges, drops, or changes an in-progress or blocked task, and which states, if any, may survive automatically?
   Answer: Preserve state only for a one-to-one task whose scope and acceptance obligations are unchanged. Reopen changed tasks and every successor of a split or merge. Archive a dropped defective constraint with reason and successor mapping; never mark it complete. The coordinator alone applies glyphs and metadata.
7. Is the initial capability Lightweight-only, preserving the current refusal for tracked definition recovery?
   Answer: Yes. Start Lightweight-only and preserve the existing refusal for tracked definition recovery until tracked authority is explicitly and separately designed.
8. After an independently reviewed redefinition is applied, may autonomous Work resume immediately, or must some classes of derived change wait for later user review?
   Answer: Resume immediately after atomic application, structural validation, fresh verification, and independent approval when the change is outcome-equivalent and derived-only. Ask the user only when outcome equivalence is ambiguous or a normative obligation would change.
9. What is the termination rule if repeated redefinitions produce no progress or keep changing decomposition without satisfying the original condition?
   Answer: Terminate semantically, not at an arbitrary redefinition count. A further redefinition requires new distinguishing evidence. If the same blocker or an equivalent decomposition returns without progress, use `no-progress-verified`; existing overall and target budgets remain backstops.

## Normalized Intent

- Reduce avoidable human round-trips during explicit autonomous Work without granting authority to alter, reinterpret, or replace user-owned intent.
- Let Work repair `plan.md` and canonical `tasks.md` when a derived-definition defect blocks legitimate progress. Let `spec.md` change only for an outcome-equivalent contradiction clarification, accidental execution-constraint relocation or replacement, or verified execution assumption.
- Preserve the promised outcome and every acceptance, safety, quality, scope, failure, and meaning-of-done obligation. The route may change; the promised outcome may not.
- Establish eligibility from either a deterministic contradiction or impossible gate causally traced to the definition, or current Feature 009 evidence that materially different implementation approaches cannot resolve the blocker. Do not require retries when the contradiction is already provable.
- Require a complete old-to-new equal-or-stronger obligation mapping, exact user-section bytes, retained checks or independently reviewed successor checks, and preservation of the intended invariant and trigger evidence when a defective literal is replaced.
- Protect automatic writes with exact ownership, one balanced managed region, exact append-only log-prefix preservation, preserved task history, one guarded atomic batch, post-write reparsing, and all-or-restored rollback.
- Preserve task state only for a one-to-one task whose scope and acceptance obligations are unchanged. Reopen changed, split, and merged work; archive dropped defective constraints with reason and successor mapping; leave glyphs and metadata to the coordinator.

## Constraints

- Never automatically edit or reinterpret user-owned intent.
- Never use redefinition to weaken acceptance criteria, remove a failing requirement, lower a quality or safety bar, or retroactively make the current approach pass.
- Any change to user intent, product scope, the safety floor, ownership, external authorization, spending, credentials, destructive authority, or the meaning of done must stop for the user.
- One independent semantic review must judge the coordinator-composed exact final four-path bytes and mappings before apply. Deterministic identities prove exact identity only; the reviewer judges outcome, obligation, task-scope, acceptance, decomposition-basis, invariant, successor-check, and any `dropped-defective` equivalence. Applying a redefinition does not approve the implementation that follows.
- Fresh lint and required verification must execute synchronously inside the atomic post-apply rollback callback against exact applied descriptors. Any failure throws into reverse rollback of all four paths; incomplete rollback remains a distinct hard failure. Post-apply validation only revalidates exact review identity and does not rerun semantic review.
- Preserve exact owner identity and coordinator-only authority over task glyphs, task metadata, boards, mirrors, execution history, and reconciliation state.
- Keep tracked definition recovery unsupported and refuse before filesystem helper entry or mutation.
- Preserve the intended invariant and triggering evidence when replacing a proven-defective literal check.
- In explicit autonomous Lightweight recovery only, a non-open task containing a trusted-evidence definition defect may be archived without another user prompt when the exact final proposal maps every obligation and check to independently approved equal-or-stronger open successors, preserves prior identity/state and terminal history, records defect and trigger evidence plus successor mapping, and inherits neither state nor completion evidence. Every ambiguity, normative change, missing successor or evidence, failed review, other Work mode, non-Work flow, and ordinary explicit redefinition retains the user-confirmation pause.
- Extend the existing recovery action, learning governance, and atomic transaction machinery; do not duplicate them.
- Do not invent a lane, command, persistent store, or additional ledger.
- Do not invent a transaction engine or objective system.
- Do not import bounded revision autonomy or `good-enough-delivery`; this capability grants no extra attempt authority and permits no lower quality.
