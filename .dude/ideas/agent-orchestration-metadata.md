# Idea: Agent Orchestration Metadata

## Idea

Dude's bundle agent orchestration needs fine-tuning. Every bundled agent needs deliberate model and orchestration metadata.

Research the official surfaces: GitHub Copilot custom-agent profiles, Copilot SDK custom-agent properties, Copilot CLI, GitHub cloud, VS Code and other supported IDE surfaces, Claude Code subagents, Agent Skills, and GitHub Agentic Workflows. Identify all relevant fields, compare them against the current Dude agent sources, and establish one canonical agent metadata authority that builds the target-specific agent representations used by development dogfood, release bundles, and optional-pack composition.

The Copilot SDK `customAgents` properties closely follow file-profile attributes, and Dude may run in GitHub cloud, Copilot CLI, VS Code/other IDEs, Claude Code, or SDK hosts, so the design must be ready across these environments rather than assuming one host. Read "ready" as source-side readiness, not as shipping every flavor; `### What maximum compatibility actually means` below is the corrected reading and governs where this paragraph and the older text conflict.

### Decisions I accepted

All 32 currently authoritative core and catalog-pack agent sources are in scope, not just the three core release agents or the 14 currently installed dogfood agents. The authoritative `.agent.md` sources under `src/agents/` and `library/packs/*/agents/` stay the per-agent authority: stable stem identity, description, tools, visibility, delegation, and the logical model classification all live in that source frontmatter, and instruction bodies stay in those same source files. `library/packs/*` remains the canonical authoring source for optional packs; it is not generated output, and pack agents remain fully in model-class scope. Target profiles and configurations are generated from the sources rather than independently edited. A second writable metadata catalog alongside the sources would only duplicate an authority that already exists, so it is out of scope. The aggregate agent index waits until a real production or documentation consumer needs one; until then the existing hand-maintained rosters stay as they are and this work neither generates nor drift-checks an index.

The bundle ships exactly one generated tree: Copilot file profiles at `.github/agents/<stem>.agent.md`, which cover GitHub.com cloud, Copilot CLI, VS Code, and other supported IDE surfaces. Claude Code subagent profiles under `.claude/agents/` and a generated Copilot SDK configuration representation under `.github/agents-sdk/` are both dropped: not generated, not shipped, not tracked, not drift-checked. They survive as documented target contracts, not as emitted files.

The architecture stays static: deterministic explicit target emitters and adapters, not a plugin framework, runtime service, database, watcher, scheduler, or new `.dude` state.

Every agent receives a stable logical model class from `inherit | fast | balanced | reasoning`, declared in source frontmatter under one canonical key, `model-class:`, and resolved through target-specific mappings. `model:` keeps its host meaning of a concrete model identifier, so the class never rides in that key, and no literal model string is the portable identity across platforms.

What I do not want is that literal string sitting in every agent file. The concrete model belongs in one central location, at a higher level of abstraction, so that changing a model is one edit in one place instead of dealing with n number of files. Agent sources therefore carry only `model-class`, and one canonical high-level configuration source under `src/config/`, proposed as `src/config/agent-models.json`, owns the concrete model family or identifier for each host and the class-level effort. Mapping and adapter modules consume that configuration; they do not own duplicate values. Our approach already runs everything through an internal build, so those existing build and projection flows resolve the class and materialize the host-specific values, and no generated output carries `model-class` back out. Generated target files may still materialize literal values where a host requires them, because that is what those hosts read, but generated output is never the source of truth and nothing here may imply that a host supports variables or references when it does not. This stays static and projection-time: no live host runtime lookup, service, registry daemon, plugin framework, or new state. `dude` stays `inherit`; the specialists are pinned by class. The approved v1 override set is empty, so overrides remain an allowed concept only once a concrete per-agent need exists, and no override machinery gets built before then.

Effort is kept, and I want to see it represented in the configuration alongside the models. This reverses my earlier call to delete effort along with the two dropped trees. It is retained as class-definition data in the configuration, not as resolution code: a class says which model and how hard it thinks, and the Copilot adapter simply does not emit the half it has no field for. `### Effort belongs to the class, and the configuration has to be extensible` below is the corrected decision and governs wherever this paragraph or any older text still reads as deleting effort.

Only Dude is normally visible in user-facing selectors. Specialists are normally hidden where the host supports it but stay internally auto-delegatable through Dude. That is a UX default, not a security boundary: Claude may still expose specialists through `@` mentions because its subagent frontmatter has no equivalent visibility field, and nothing here may claim stronger enforcement than the host provides. Direct specialist invocation stays permitted, and specialists keep the existing coordinator-only boundaries, so they cannot bypass definition lifecycle, task-state ownership, independent review, or close protocol. The workflow stays safe because authority lives in role contracts, not selector visibility.

Dude may delegate to the full roster. Specialists are leaves by default, only explicitly declared composite roles may delegate, and canonical references use stable agent IDs or stems rather than display names.

Agent Smith is one of the migrated records and must be updated in the same foundation. Its body and rules must teach canonical agent metadata, target-specific field semantics, model and effort mapping, invocation degradation, tool and MCP mapping, official-doc drift, and generated-output boundaries. It stays the agent-authoring authority, uses the scaffolder for creation, and delegates mechanical enforcement to Dude lint. It never authors Skills or gh-aw workflows and validates only cross-references.

Agent Skills and gh-aw workflow frontmatter stay separate artifact families. Agent records may reference skill IDs for SDK or Claude preload where supported. gh-aw workflows reference agent IDs, while workflow triggers, permissions, engines, tools, and safe-output fields never enter agent frontmatter.

Development dogfood, release builds, and `compose add/remove/verify` must project and own the appropriate target files deterministically, including cleanup and removal parity. `compose add` resolves each pack agent's declared `model-class` at install time through the shipped Copilot adapter and packaged configuration. No target output may be emitted before its ownership, stale-file cleanup, and uninstall behavior are complete.

Nothing degrades silently. Unknown canonical fields, unmappable explicit model, tool, or invocation policies, identity collisions, unresolved delegation IDs, unsupported empty-tool semantics, and stale target outputs must fail or produce explicit target-specific warnings under a defined degradation contract. Host-specific unknowns must never silently become portable assumptions.

### What maximum compatibility actually means

This corrects how my original idea should be read, and it supersedes the earlier "keep all three projections in scope" reading.

When I mention in my original idea maximum compatibility, all that is not to provide all the flavors in one package, but adding the necessary or maybe needed front matter that in the future I can easily adapt to either Claude and Copilot SDK. So for now let's follow YAGNI: we drop both, and we enrich the current bundle frontmatter for any missing key that might be needed.

If we consider `/src` as source code, we can keep any frontmatter we want, and only in the mapping phase that produces the actual output to be used, we can pick and translate whatever we want to. For example, if our source contains the effort, the prompt, delegation, visibility, all the fields we want, we can have different maps to produce different outputs. Right now we're targeting GitHub Copilot and VS Code / Copilot CLI, and we can have an adapter producing only those outputs. So right now the bundle is generic for VS Code, however it will be very easy to target a different format or target if we create an adapter in the middle that produces those frontmatters. So if we don't include them now, as long as we clarify that adapter scenario, that's fine — for example: right now we do this in the bundle for Copilot; if you want to produce a bundle for SDK then you're going to take this frontmatter and then we're going to produce this adapter and take this output.

So: `src/` is the authoring source of truth for core code and shared configuration, while `library/packs/*` remains the authoring source of truth for optional packs. Adapters translate those sources at the output boundary. The shipped adapter targets Copilot file profiles. Another target is added later by writing another adapter, not by enriching the bundle with more generated trees.

Extra frontmatter is still not free. An unsupported field can silently do nothing, collide with a target-specific meaning, or fail host validation. The source may be rich, but rich does not mean speculative: a source field has to be consumed by the shipped adapter. Under that test I checked the current keys and none are missing — `name`, `description`, `tools`, `model-class`, `user-invocable`, `agents`, `argument-hint`, plus the body are already a complete superset from which every field of all three host contracts is derivable. So no new frontmatter key gets added. The adaptability I asked for already lives in three seams that exist today: the logical `model-class` rather than a literal model, the coarse tool vocabulary that translates per host, and stable stems for delegation.

That test governs source frontmatter keys and shipped code paths, and it is why no new source key is added and why no effort resolution code is built for a host with no effort field. It is not a reason to strip effort out of the class definition. Under source-as-code the configuration carries the full declarative intent and each adapter selects the subset it can express; the configuration states that selection explicitly rather than leaving it implied. See `### Effort belongs to the class, and the configuration has to be extensible`.

### Provisional target family policy, plan input rather than spec content

I approved this mapping as the starting point for implementation, and it is deliberately kept out of the technology-agnostic assignment table in `spec.md`. It is provisional: exact spellings and identifiers get verified against official documentation at plan and implementation time, and none of them ever becomes the portable identity.

- Copilot file profiles, the one shipped target: `fast` -> GPT-5.6 Luna family, `balanced` -> GPT-5.6 Terra family, `reasoning` -> GPT-5.6 Sol family, `inherit` omits the model.
- Copilot SDK and Claude are no longer emitted, so their families are documentation for the adapter contract rather than live mapping entries: SDK follows the same GPT-5.6 families as the file profiles; Claude maps `fast` -> Haiku family, `balanced` -> Sonnet family, `reasoning` -> Opus family, and `inherit` keeps the documented inherit behavior.
- Class-to-effort intent, now carried as class-definition data in the configuration rather than as documentation only: `fast` low, `balanced` medium, `reasoning` high, `inherit` none. Copilot file profiles document no effort field, so the shipped adapter declares that it does not emit effort; the value is still declared on the class.

### The mapping values live in configuration, not hardcoded in the script

"Also, let's make sure all the mapping or at least the values are configuration-driven rather than hard-coded in the scripts. So I want a configuration or a setting file where I can say, you know, the models there for all the stuff."

What survives after dropping both non-Copilot targets is a small amount of mapping data, and that is exactly why moving it into data is cheap and worth doing rather than over-engineering. The agreed shape, with the exact filename and on-disk schema left as plan detail:

- One canonical configuration source holds the values in an accessible high-level location under `src/`, proposed as `src/config/agent-models.json`. It is not canonically authored inside a skill directory.
- `provenance`: a dated string recording where the model identifiers came from and that they are runtime-observed rather than an officially enumerated list.
- `classes`: an object keyed by class name, each class carrying its host-neutral settings. The inheriting class carries none; the others carry an effort level.
- `targets`: one key per adapter target, each declaring `emits`, the settings that adapter actually writes, and `models`, mapping every declared class to its concrete model for that target, with the inheriting class carrying no model.
- `agent-model-map.mjs` becomes a thin loader and validator rather than the data holder. It reads the configuration, validates it fail-closed, freezes it, and exposes the same resolution function.
- Provenance moves into the data. JSON carries no comments, and the dated evidence for the model identifiers currently lives in a code header; it has to travel with the values so it cannot rot separately from them.
- Development and release builds copy or compile the source configuration into the shipped engine location used by build, compose, lint, and scaffolding consumers. That packaged copy is generated output, never a second authority, and is not hand-edited.
- Honest constraint, stated rather than glossed: the source configuration is a build input, not a live runtime knob. Generated agent profiles bake in the resolved model, so editing the source file changes nothing until the dev bundle is rebuilt, and installed packs additionally require the documented `compose remove` plus `compose add` refresh. Say that plainly in the outcome and in the adapter-contract documentation so nobody is misled into expecting an immediate effect.

That is one authoritative configuration source, validated by every consumer through its packaged build output. Anything beyond that is where configuration-driven turns into a settings system, and the non-goals below draw that line.

### Pack and configuration source topology

The considered alternative of moving optional-pack authoring sources under `src/packs/` and committing `library/packs/` as generated output is rejected for this feature. It would create source/output drift, duplicate diffs, migration work, host-specific catalog lock-in, and developer-build burden disproportionate to the model-mapping need. `library/packs/*` remains the canonical optional-pack source, and this decision introduces no generated pack catalog.

The canonical model and effort values live only in the high-level source configuration under `src/config/`. There is no hardcoded fallback map, duplicate value set under `library/`, or static pack-specific model definition. Core and pack agent sources declare the same logical `model-class`; development and release builds package the shared configuration for engine consumers, and `compose add` uses that packaged copy when it projects a pack agent at install time.

Continuous integration verifies generated dogfood and release drift. It does not create pull requests or commit generated changes.

### Effort belongs to the class, and the configuration has to be extensible

"Would like to see the effort as well represented there. That configuration needs to be extensible so I can add more or less as needed."

This reverses the earlier decision to delete effort. Retaining it is consistent with source-as-code rather than a YAGNI violation: the configuration carries the full declarative intent and each adapter selects the subset it can express. A class is a semantic statement — which model, and how hard it thinks — so effort is part of the class definition, not a host detail. The Copilot adapter simply does not emit the half it has no field for.

Effort is per class, not per target. All three host mappings previously used the same effort for a given class through one shared table, so putting effort on the class is faithful to the existing behaviour and avoids repeating it per target. A per-target effort override is explicitly not added now; if a future host needs a different effort for the same class, that is added then.

`emits` exists so the file states in data that an adapter knows about a setting and deliberately does not write it. Without it, effort would be unexplained data sitting in a file. It also keeps validation closed, so extensibility does not degrade into accepting anything.

Extensible means extensible on three axes, with fail-closed validation intact:

1. Adding or removing a class means editing the class set and each target's model map, with validation requiring exact coverage so a half-added class fails the build rather than silently resolving.
2. Adding a target means one new key, and a future Claude-style target would declare that it emits both model and effort.
3. Changing what a target writes means editing its `emits` list.

Every key stays known and validated. Unknown class names, unknown setting names, missing coverage, and malformed values must all fail closed, naming the offending target, class, or setting.

Honest limitation, recorded plainly rather than glossed: effort with no emitting adapter is declared intent, not exercised behaviour. Validation can confirm it is a known, well-formed value; nothing proves it is the correct value until an adapter emits it. That is a real difference from the model value, which every build exercises, and this ledger says so rather than implying the two are equally verified.

### The documentation deliverable is the adapter contract

The substitute for the two dropped trees is not a manual how-to for hand-writing Claude or SDK files. It is an adapter contract that records the source frontmatter schema, the per-target field correspondence for Claude subagents and Copilot SDK configuration, and how to add a renderer. Developer documentation also explains where the canonical configuration lives, how `build-dev` and release builds package it, why compose needs the packaged copy at install time, how to rebuild after source or configuration changes, and which files are authoritative versus generated. That keeps the extension path a code path and preserves the vendor research as prose instead of discarding it with the deleted code.

### Non-goals

- Do not combine Skill schemas or gh-aw workflow schemas into agent source frontmatter.
- Do not generate, ship, track, or drift-check a `.claude/agents/` tree or a `.github/agents-sdk/` tree.
- Do not add a source frontmatter key that the shipped Copilot adapter does not consume.
- Do not add a per-target effort override; every target uses the class effort until a concrete host need is stated.
- Do not accept arbitrary or open-ended settings without validation just because the configuration is extensible.
- Do not claim the effort values are verified against a host that does not consume them.
- Do not replace the dropped trees with an opt-in flag, a gated emitter, or a dormant renderer; a later target arrives as a new adapter.
- Do not stand up a second writable agent metadata catalog beside the authoritative agent sources.
- Do not build, generate, or drift-check an aggregate agent index while no production or documentation consumer reads one.
- Do not move optional-pack authoring sources under `src/packs/`, treat `library/packs/` as generated output, or introduce a generated pack catalog.
- Do not add a runtime registry service, daemon, watcher, scheduler, database, generic adapter discovery/plugin system, or alternate project-state manifest.
- Do not weaken current coordinator-only authority, verification, review, or close requirements.
- Do not assume selector visibility is security enforcement.
- Do not hardcode one vendor model identifier as the portable agent model.
- Do not scatter concrete model identifiers or effort literals across agent sources; they live in the one canonical source configuration.
- Do not canonically author the model configuration inside a skill directory, leave a concrete model identifier or effort literal hardcoded in a mapping module, duplicate values under `library/`, or add static pack-specific model definitions.
- Do not add a built-in default or fallback map that masks an invalid, incomplete, or missing configuration file.
- Do not add environment-variable overrides, per-project or per-user configuration merging, runtime configuration discovery, or layered settings resolution for the model configuration.
- Do not introduce a schema framework or a settings framework for one build-time configuration file.
- Do not present the configuration file as a live runtime knob that takes effect without a rebuild, or without the documented pack refresh for installed packs.
- Do not hand-edit generated dogfood or target projections as their source of truth.
