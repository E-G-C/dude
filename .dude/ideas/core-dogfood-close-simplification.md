# Idea: Core Dogfood Close Simplification

## Idea

> I want simplification as much as possible. I'm about even considering removing the whole feature altogether

> Retire it entirely

The selected outcome is complete retirement of the project-local automatic core dogfood promotion feature and policy. No thin final-close convention remains.

Complete retirement means:

- Delete the project-local `.github/skills/dude-local-core-dogfood-promotion/` skill.
- Remove the large `## Core Dogfood Close` procedure from the project skill.
- Remove the definition requirement for a terminal open, non-`[P]`, `[Shared]` task with a `declared-src:` clause.
- Retire dogfood-specific baseline lines, declaration and evidence digests, accepted lines, review-envelope binding, special routing, and close machinery.
- Remove or replace the static T007 policy-contract tests and related ceremony-specific assertions that exist to enforce that policy.

Historical idea, spec, task, archive, execution-history, and Coordinator Log records remain history. Retirement does not rewrite or delete those records merely because the live policy no longer applies.

Retirement also does not remove useful development and release mechanisms. Keep `scripts/build-dev.mjs`, authoritative source-to-generated byte parity, CI's dev-bundle drift check, ordinary focused and full tests, Dude lint, compose and release verification where appropriate, and independent review under normal feature close.

The developer's core workflow becomes straightforward: edit `src/**`, run focused tests, run `node scripts/build-dev.mjs` for an informational preview, reload or restart the active VS Code agent session when required, exercise one named behavior against `.github/`, and iterate. When ready, run fresh normal final verification and independent review, ensure parity, and commit authoritative `src/**` with generated `.github/` core. There is no dogfood terminal, baseline line, canonical evidence digest, accepted line, or special close skill.

Pack work remains separate: edit `library/packs/<name>/`, run pack-focused tests and compose verification, live-test in a disposable install, and commit pack source. It does not use core `build-dev` promotion. Project-local `.github/skills/project`, `.github/skills/dude-local-*`, workflows, and `.dude` are direct project-owned surfaces rather than generated core.

Required workflow documentation remains part of whichever implementation retires or simplifies the policy. It must update existing contributor docs with ownership classification plus the concise pack-change and core-change examples captured in Core Dogfood Preview. If direct `build-dev` preview needs no separate definition, this close-retirement or simplification work consumes that documentation requirement instead of duplicating ownership.

The user did not choose a thin convention. Risk tiering, changed-set policy, replacement content or failure baselines, review-envelope alternatives, bookkeeping recovery, and ceremony-specific performance tiers are not part of the retirement feature.

The verified coupling is broader than deleting two Markdown procedures: `scripts/current-format-contract.test.mjs` contains the ceremony's static policy and Feature 009/T007 contract assertions, while `scripts/build-dev.test.mjs` uses the local promotion skill as a protected project-local fixture. Those tests need deliberate removal or replacement. Generic independent-review-envelope handling in `dude-work` serves broader execution evidence and is not part of dogfood-policy retirement.

### Earlier Captured Context

The following text is preserved verbatim from the earlier brainstorm. The retirement-first framing above supersedes it as the primary path; its detailed design concerns remain deferred unless the user chooses a thin convention.

This separate, deferred draft covers only the ceremony for final accepted core promotion and close. Core Dogfood Preview can ship independently and is not blocked on this idea; close simplification is not required for preview.

The existing project-local, non-shipped policy may be doing more work than its highest-yield guarantees require. This idea should examine proportional final-close ceremony while preserving candidate non-negotiables: byte parity, protected-boundary preservation, independent review, and fresh final verification.

The observed friction to evaluate is bounded to final accepted promotion and close:

- **Risk tiering or proportional ceremony.** Full ceremony may be justified for execution-runtime changes but excessive for lower-risk core changes.
- **Global changed-set scope.** Ordinary checking is subset-based, not strict equality: every actually changed source path must be declared, while a declared path need not change. The changed set is still computed across all `src/**`, so unrelated source edits can block or require adoption.
- **Baseline fragility.** Binding both `HEAD` and `HEAD:src` means an ordinary commit can invalidate a recorded baseline even when relevant source content is unchanged.
- **Known pre-existing failures.** The zero-failure requirement can make an unrelated existing failure block final close, with no current "no new failures" model.
- **One-time carve-outs.** Feature 009 and T009-specific exceptions remain embedded in general policy.
- **Review-envelope brittleness.** Interruption can make an exact substantive review response unavailable and force a complete fresh review.
- **Coordinator bookkeeping discrepancies.** Lane-state disagreement is not a named general policy gate, but observed task-state and owner-log inconsistencies still caused rejection, repair, full reverification, and rereview in practice.

CI repair remains a separate concern. Preview behavior, projection, and cleanup belong to the independent Core Dogfood Preview idea rather than this draft.
