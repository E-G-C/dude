# Idea: Automatic Core Dogfood Promotion

## Idea

Automate this repository's internal dogfood promotion for the main Dude core developed in `src/`. This does not apply to optional packs under `library/packs/` or to technical-docs work. Dogfood promotion means projecting accepted core source changes into generated `.github/` core as a final feature-close requirement; it is distinct from release promotion such as merging, tagging, or publishing.

The reusable promotion procedure lives in `.github/skills/dude-local-core-dogfood-promotion/SKILL.md`. Dude discovers and loads this project-local skill only when the canonical terminal promotion task becomes ready, after every source-contributing task and all acceptance prerequisites, including fresh verification and independent review, are satisfied. Completing a spec alone never makes the terminal task ready, loads the skill, or materializes anything.

When the terminal task is ready, the skill promotes an accepted feature that changed core `src/` by running the existing `node scripts/build-dev.mjs` before final feature close. The resulting generated `.github/` core changes become part of the same feature delivery. If the feature changed no core source, promotion is a verified no-op.

Add a fail-closed first-adopter bootstrap for the initial live use of this procedure. Preserve the original valid pre-source baseline as the immutable comparison base and never retroactively rebaseline modified source. Continuity may cross an explicitly authorized commit or merge only when current `HEAD` descends from that baseline, the independently accepted source identity is unchanged, every changed `src/**` path is declared, generated core remains exactly at the baseline projection, and no unrelated or concurrent owned-boundary drift exists.

Prioritize completing Feature 009 `T009@696e6369` as the one-time first live adopter in the current main checkout, with no isolated worktree. It may materialize and validate core under the accepted Feature 008 `T006@62726964` procedure before Feature 008 `T002@5b7d930e` and `T003@c4e6812d` perform final bootstrap acceptance; Feature 008 itself does not need to be completed before T009.

The prior bridge correctly stopped under its then-current contract: the immutable-original-baseline delta contains 20 `src/**` paths, while T009's accepted live declaration contains its 10 Feature 009 paths. The 10 additional paths arrived through merged main and remain separately owned bundle-import, agent-frontmatter test, and lint work. Retain T009's accepted ten-path declaration and ownership. Do not make T009 claim implementation, acceptance, or closure of those 10 inherited merged paths.

Supersede the requirement that the bridge consume historical durable accepted HEAD, source, or dual-review identity fields from Features 003 or 006 or from Feature 009 T008. Those fields were never recorded and cannot now be reconstructed without fabrication. For this exact one-time T009 materialization event, allow a fresh current-session cross-feature acceptance packet to authorize the complete current 20-path original-baseline delta and the complete expected generated projection. Before materialization, derive that acceptance from current Git trees and bytes, exact current owners and tasks for attribution where available, Feature 009 T008's exact declaration and changed evidence, current source and generated inventories, the existing materializer mapping, current HEAD, protected-boundary prestate, focused source, policy, and runtime checks that do not require current parity, exact proof that the packet-described projection delta is the sole isolated parity failure, and fresh independent Tester and Reviewer approval grounded in independently reacquired or verified authoritative evidence.

Fresh cross-feature acceptance is materialization authority only. It does not retroactively rewrite or close Features 003 or 006, transfer ownership, expand T009's declaration, or claim that historical evidence existed. If the work is interrupted, or any byte, HEAD, authority, or expected projection changes, discard the transient packet and reacquire it from fresh current-session evidence; never reconstruct it. Require no persistent pre-acceptance ledger. Record normal final T009 accepted evidence only after materialization, final verification, and final independent review.

Keep every fail-closed gate that does not depend on the unavailable historical fields: the original baseline remains the immutable comparison anchor; current HEAD descends through explicitly authorized continuity; the current 20-path delta and complete expected projection are exact; source and base-generated boundaries are clean apart from the expected unmaterialized projection difference; hidden, ignored, and index dirt is absent; protected project boundaries remain unchanged; and no concurrent work overlaps the event. Generated core is never hand-edited, no baseline is invented, and nothing automatically commits, pushes, tags, or publishes.

Keep this exception exclusive to the current T009 event. Later features retain ordinary exact baseline and declaration-equals-changed rules. Revise open `T007@9a4e7c12` in place and keep it solely ready; keep completed Feature 008 tasks done, `T002@5b7d930e` blocked, and `T003@c4e6812d` open.
