# Design Proposal: Dude Canvas Workspace Integration

## Outcome

Make Canvas recognizable as the graphical workspace established by 052 while keeping the discovery, capture, response, and Review capabilities delivered by 057. A user can find a feature, understand its exact next step and blockers, inspect its individual tasks, answer a current request or review its mock, and return without losing the selected feature or context.

052 remains the broader product direction: a task-specific graphical layer over the same active agent session that minimizes routine chat. Its first read-only increment was a completion boundary, not an interaction ceiling. Its broader Work/task-detail intent supports this selected-feature inspection within 062; unrelated deferred capabilities remain outside this increment.

## Scope And Surfaces

In scope is one integrated Dude Canvas: the desktop workspace shell, one work finder, selected-feature Now orientation and read-only Tasks, Needs You, New idea, and user-entered HTML Review. Preserve captured intent, source-backed progress and activity, all six response classes, same-agent acknowledgment, saved review work, and sealed report/image evidence.

Keep 052 and 057 closed. Their specifications, mocks, approvals, reviews, and task history remain untouched. In particular, 057's rev-8.2 is a separately approved historical direction; this package neither withdraws that approval nor asserts that it matched 052's composition.

Out of scope are general editing of existing ideas or artifacts, arbitrary Dude commands, task Run/Stop/Retry/Edit/Mark done controls, a generic artboard or any-file viewer, automatic Review opening, new annotation manipulation, Team/Packs/Memory management, a second tracker or backlog manager, and new workflow or request persistence. The necessary read-only exposure of selected task information does not add an execution engine, agent monitor, handoff, mutation route, or evidence format.

Settings (063) and Kanban are outside 062. The tentative Dude Settings suggestion, including packages and a bottom-left cog, remains separate; the historical approval decided none of its contents or operations. Add no Settings destination or placeholder cog.

053 critique, 054 auto-open, 058 intake policy, 059 annotation manipulation, and 056/060/061 recovery or capacity work remain separate. References to them establish no dependency or execution order. Other deferred 052 capabilities remain future product work, not canceled intent or hidden requirements of 062.

## Visual Intent

### Should Feel

- Like 052's compact desktop application: persistent context, a focal Next region, useful central work, and nearby evidence.
- Familiar across discovery, task inspection, response, and Review, with enough space for each task rather than a chat transcript in a frame.
- Honest about what is current, recorded, incomplete, or unavailable.

### Should Never Feel

- Like a permanent narrow dashboard inside a wide host, or a wall of equally emphasized cards.
- Like a new product that discarded useful work or silently replaced the accepted direction.
- Like a navigation prototype whose future buttons imply working capabilities.

## Brand Fit

Retain the established Fluent 2 visual language, component anatomy, host light/dark appearance, compact spacing, and accessible interaction states. Do not introduce a palette, typography system, or framework. Density must not reduce readable instructions, visible focus, or WCAG 2.2 AA contrast and target sizing.

The familiar desktop workspace pattern used by VS Code fits this task: stable context and activity navigation surround a focused work area, with secondary properties disclosed nearby. Use its list-and-inspector convention for task detail within Now, not as permission to add an editor, command palette, or unrelated management surfaces.

### Entry and discovery

Keep **Overview** as the initial entry with no work selected and **Open** as its initial scope, with **Closed / All** available. The one main selector presents either unselected search/filter controls or the committed **Working on** value with subordinate **Clear**, never both, in every view. Discovery uses the command-bar workspace and available results area rather than a permanent feature sidebar.

Ordinary Overview navigation keeps the selected work filter and other return state. While selected, Overview shows only that record as selected work, with matching copy and counts; it must not say **Nothing is selected**, expose search/scope controls, or offer a global switchable work list. Activating that same selected row may reopen Now. Remembered lookup settings do not loosen or replace the committed filter.

**Clear** removes the selected work filter, opens Overview's same finder, and focuses its existing search in one activation. The historically approved reference and corrected mock use the definition owner's recommended unfiltered reset: an empty query, **All** records, and lookup scroll/keyboard row position reset to the start, so an earlier query cannot trap discovery. **All** is a conservative interpretation of the user's "clear the filters", not a literal enum answer from the user. This reset does not change the initial-launch Overview/Open default; ordinary view returns still preserve selection and applicable finder state. Add no **Switch work**, second picker, extra reset control, or confirmation.

Clear affects only the work lookup and its selected-task inspection. It does not delete or close work, cancel or answer a request, reset request-scoped filters or forms, erase drafts or Review markup, submit anything, or transfer approval. Needs You keeps independently scoped current requests accessible, and New idea remains unfiled rather than inheriting the work filter.

Choose a row to enter **Now** for that exact record. Show the existing zero-padded lifecycle number, name, status, and progress together, ordered by ascending capture number, oldest first. A blank workspace offers New idea. An empty Open filter offers Closed/All and does not masquerade as a blank workspace. Incomplete work status keeps unknown records discoverable with an explanation.

This disposes of recorded question 1 as a definition-owner proposal: retaining the shipped Overview/Open behavior is less disruptive than inventing a selected feature or landing on an arbitrary request. Moving its one finder into the command-bar composition reconciles discovery with 052 without duplicating selection. It is not a user-supplied answer.

### Task inspection in Now

Tasks incorporates Phases rather than adding a competing progress view. Start with all canonical rows visible in their existing phase and source order. Each row shows its title, phase association, and recorded status. Highlight every recorded in-progress task with text and a non-color-only indicator; distinguish that indication from the row selected for inspection. Neither a glyph nor a connected session proves a live agent is working.

Use a section-local status filter with **All** initially, plus **Pending**, **In progress**, **Blocked**, and **Done**. Filtering does not change feature selection, the main search/Show controls, Next, or a request's target. Keep phase totals labeled as unfiltered totals and show the matching-row count separately. An empty filter says there are no matching tasks, not that the feature has no tasks. If filtering hides the inspected row, dismiss that detail and retain focus on the filter.

Activating a task opens one read-only detail in the existing desktop dock; at narrow widths, the same content expands in flow immediately after its row. Opening, closing, and ordinary return preserve the feature context. Show the full available canonical unit, including body, acceptance, and context text, with dependencies and any explicit blocker reason. Source text remains inert and readable, including code or markup examples. Missing instruction, phase, dependency, or blocker information is named rather than reconstructed.

Pending is recorded not-started work. Within it, distinguish satisfied task dependencies from waiting dependencies when those facts are available; task-dependency readiness grants no approval or execution permission. Explicitly blocked work remains distinct from dependency waiting. Defined/all-open file-backed packages still show planned tasks and **Not started**, without a running-agent claim or a manufactured next execution action. A draft with no package has no task definitions. Tracked work uses its exact authoritative mapping; missing mapping or coverage is unavailable, never a markdown fallback or an empty-list guess.

Recorded task verification and review outcomes appear only with an explicit binding to that exact feature and task and a source that actually exposes the result. Acceptance criteria, a Done glyph, generic test files, feature activity, and design-review history are not proof of task verification. Use **Not recorded** only when the authoritative source establishes absence; otherwise use **Not exposed by this source** or **Unavailable**. A historical outcome keeps its recorded time/revision where supplied and does not certify the current task.

Rows, detail, phase totals, and selected progress must come from one agreeing read. Retain the existing last-read/source-identity and freshness behavior; never label a prior task's body as a new feature or mix old detail with new counts. A feature change or Clear removes the task selection and local filter before the next context is presented. Ordinary return may retain them only for the same exact feature and surviving task key.

## User Scenarios & Testing

### US1 - Find the right work without an implied choice (P1)

As a returning user, I want one recognizable way to find ideas and features so I can select the right context without knowing a slug or accepting an inferred priority.

**Independent test:** Open a populated workspace with no selection, drafts, completed features, resolved ideas, unknown work status, and names whose alphabetical order differs from capture order. Include Overview with All selected -> choose 002 -> Now -> Overview without Clear, then explicit Clear after a narrowed lookup.

1. **Given** several records and no selection, **when** Canvas opens, **then** Overview and its Open finder appear without choosing a record by number, recency, title, or task count.
2. **Given** readable records and no committed selection, **when** the user browses, searches, or changes Open/Closed/All, **then** every matching record is reachable with its number, name, status, and progress or explicit unknown value.
3. **Given** a visible result, **when** the user activates it and later returns to Overview without Clear, **then** Now and Overview retain that exact selection. Working on/Clear replaces discovery controls in both views; Overview shows only the selected work row with truthful selected-work copy/counts. It offers neither a Nothing-is-selected caption nor other work to switch to. Reopening that row returns to the same Now; ordinary navigation preserves applicable finder state.
4. **Given** committed work found through a nonempty query, narrowed scope, and moved lookup position, **when** the user activates Clear, **then** selection ends and the same Overview search receives focus with an empty query, All records, and lookup scroll/keyboard position at the start. Another record is reachable without undoing the old query. Independent requests, their filters/forms, drafts, and Review work are unchanged.
5. **Given** incomplete work enrichment and no selection, **when** the finder renders, **then** unknown records remain discoverable and the affected coverage is explained rather than silently excluding them.
6. **Given** any view with or without selected work, **when** the user expands or collapses the rail by pointer or keyboard, **then** the current view and work filter remain unchanged, labels and focus stay usable, and unsent input and an active Review's pinned frame are preserved.

### US2 - Understand the selected feature and its individual tasks (P1)

As a user resuming one feature, I want to inspect what each task requires and its recorded progress or problem so I can understand what is happening without reconstructing it from raw files.

**Independent test:** Select exact records with draft, defined/all-open, active, blocked, completed, and conflicting/unavailable authority. Use captured 062 task units, completed 052 units, and visibly controlled mixed-state cases. Include multiline body/acceptance text, task-like examples inside source text, and refresh or feature changes while a detail is open.

1. **Given** supported current orientation, **when** Now opens, **then** Next shows the full available instruction, lifecycle and progress agree with their authority, and blockers explain their reason and source.
2. **Given** readable task definitions, **when** Tasks opens, **then** every canonical task has one row in its recorded phase order, with a title and status. Done, recorded in-progress, pending, and explicitly blocked states are distinguishable without relying on color.
3. **Given** several pending tasks, **when** dependency information is available, **then** satisfied dependencies and waiting dependencies are distinguishable from explicit blocking. Unknown readiness is labeled unknown; no task is shown as executing merely because it is eligible.
4. **Given** a selected task with a long multiline unit, **when** the user opens its detail by pointer or keyboard at desktop or narrow width, **then** its full available body, acceptance/context, dependencies, and blocker data are readable. A header-only excerpt cannot stand in for the unit, and embedded markup cannot execute.
5. **Given** a Done task with no exposed task-specific test/review result, **when** detail opens, **then** Done remains a recorded task state and the result is explicitly not exposed. If an exact task-bound historical result is available, its original outcome and source are shown without certifying a later revision.
6. **Given** 062's all-open file-backed package or a draft without a package, **when** inspected, **then** the former shows its five planned/not-started tasks while the latter explains that no task definitions exist. Neither implies live execution. Generated board entries and archives do not become extra tasks.
7. **Given** an inspected task, **when** the user filters Tasks, returns through Overview, clears work, or selects another feature, **then** only the intended local inspection changes. Selected-only Overview, independent requests/drafts, and Review remain intact; no old detail is relabeled for the new feature.
8. **Given** unavailable authority, an unmapped tracked task, or a source changing during refresh, **when** a complete agreeing view cannot be established, **then** the target and safe facts remain identifiable, task coverage is explicitly unavailable, and old detail is not combined with newer counts. A frozen browser preview never claims to track an agent.

### US3 - Respond or review, then return in context (P1)

As a user with a current human request, I want to respond in the workspace and return to what I was doing without losing an answer, annotations, or my place.

**Independent test:** Start with a selected feature and current owner-qualified fixtures for each of the six request classes, including a session request and a request for another feature. Exercise Review on successive canonical revisions and reopen sealed evidence.

1. **Given** a current request, **when** it is opened from Now or Needs You, **then** the appropriate form shows what is needed, why a human is required, what it unblocks, and its exact scope. Unrelated requests stay accessible.
2. **Given** a submitted response, **when** the owner has not yet acknowledged it, **then** Canvas shows delivery/acknowledgment status, not acceptance or application. A later declined, deferred, accepted, or applied result remains distinguishable.
3. **Given** an eligible current preview request, **when** the user enters Review, annotates, and sends feedback, **then** the report and actual image reach the same waiting agent once, with the existing source/revision checks and saved evidence.
4. **Given** a valid unchanged review, **when** the user returns and reopens it, **then** browsing selection, relevant unsent input, request identity, working markup, focus/caret, and reviewed viewport remain useful. No successor request inherits an answer or approval.
5. **Given** a revised mock, **when** the user reviews again, **then** a fresh current request is required. Feedback is separate from explicit approval of that currently viewed revision; sealed history never becomes a live approval or send surface.

### US4 - Keep capture and later work useful (P2)

As a user starting or setting work aside, I want the existing capture and discovery paths to survive the visual integration.

## Applicable Concepts

- **Browsing context:** The exact selected idea or exactly owned feature, applied as the selected work filter and distinct from the lookup query and a human request's scope.
- **Orientation:** Source-backed next step, lifecycle, progress, blockers, activity, and their freshness, not a new work-state model.
- **Task inspection:** A read-only view of one existing canonical unit, bound by feature, durable task key, and source read. Local row selection is not work selection or execution.
- **Recorded outcome:** A task-bound source statement about a particular verification or review, distinct from instructions, completion state, feature history, and current activity.
- **Human request:** A current owner-qualified interaction with scope and revision; recorded intent or history is not one.
- **Review evidence:** Working markup and sealed submissions bound to their original source; persistence supplies evidence, not live authority.

| Case | Required visible behavior |
| --- | --- |
