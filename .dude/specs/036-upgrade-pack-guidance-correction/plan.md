## Chosen Design

### 1. Correct the authoritative bundle-upgrade skill

In `src/skills/dude-bundle-upgrade/SKILL.md`, change only the two stale
installed-pack update claims:

- In `## Ownership Boundary For Generated Agent Profiles`, preserve the rule
  that core upgrade does not project or repair installed pack profiles, then
  state that a pack source or model-mapping change reaches an installed pack
  through `compose refresh <pack>`.
- In `## Boundaries`, preserve the core-versus-pack ownership boundary and state
  that installed pack profiles refresh through `compose refresh <pack>`.

Neither location may require, recommend, or offer `compose remove` followed by
`compose add` for an update. Do not change upgrade mechanics or add fallback
language. (FR-001, FR-003 through FR-005, FR-007; SC-001 through SC-003, SC-005)

### 2. Correct the public upgrading guide

Rewrite only `docs/upgrading.md` `## Refreshing installed packs`:

- retain that a core upgrade refreshes base files only and preserves installed
  packs rather than projecting them in place;
- lead the explicit installed-pack update instruction with the literal
  `compose refresh <pack>`;
- explain concisely that refresh re-projects the installed pack from its current
  source; and
- remove the remove/add command sequence and any text that presents it as an
  update or fallback.

Do not add compatibility qualification for old engines. Do not remove or
redefine ordinary installation or uninstallation guidance elsewhere.
(FR-002 through FR-005, FR-007; SC-001 through SC-003, SC-005)

### 3. Add one focused documentation contract

Extend `scripts/current-format-contract.test.mjs` with one focused test named
`installed pack refresh guidance stays current and generated`.

Using the suite's existing section and normalization helpers, require:

- the ownership-boundary and boundaries sections of the authoritative upgrade
  skill each identify `compose refresh <pack>` for installed-pack updates;
- `docs/upgrading.md` `## Refreshing installed packs` leads the update path with
  `compose refresh <pack>`;
- those bounded update sections contain no remove-then-add recipe or legacy
  update fallback;
- ordinary add/install and remove/uninstall meanings remain present in their
  existing compose guidance; and
- `.github/skills/dude-bundle-upgrade/SKILL.md` is byte-identical to its
  authoritative source after projection.

Include a small in-memory deletion or stale-recipe substitution falsifier so the
test proves its own required refresh and prohibition checks. Avoid broad
free-prose contradiction regexes, a new parser, a new test file, or engine
fixtures. (All FR; SC-001 through SC-006)

### 4. Regenerate and verify the bounded slice

Run `node scripts/build-dev.mjs` after the source edit. The only intended
generated semantic change is
`.github/skills/dude-bundle-upgrade/SKILL.md`; do not edit it directly.

Run the focused documentation contract and existing build projection test, then
the established bundle-change gates over one unchanged revision. Inspect the
changed paths and semantic diff to confirm there is no engine or memory change
and that remove/add remains only ordinary uninstall/install guidance.
(FR-006, FR-007; SC-003 through SC-006)
