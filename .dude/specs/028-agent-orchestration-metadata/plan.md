### 1. Canonical configuration and packaged copy

Create `src/config/agent-models.json` with exact root keys `provenance`, `classes`, and `targets`. `classes` contains `inherit`, `fast`, `balanced`, and `reasoning`; the three non-inheriting entries carry their accepted effort values. `targets.copilot` contains `emits: ["model"]` and an exact model entry for every class, with `inherit` mapped to `null`. Concrete model identifiers appear in this file rather than in this plan or any independently authored code.

`src/skills/dude-engine/lib/agent-model-map.mjs` becomes a dependency-free loader, validator, freezer, and resolver:

```text
loadAgentModelConfig(absolutePath) -> frozen validated configuration
resolveCopilotModel(config, modelClass) -> { model?: string }
```

`loadAgentModelConfig` reads exactly the supplied absolute path. It has no `import.meta.url` default, implicit relative path, search, fallback, environment override, embedded map, or eager module-level load. A missing argument, non-absolute path, unreadable file, or invalid document fails.

Validation is all-or-nothing:

1. The document is a JSON object with exactly the three root keys.
2. `provenance` is a non-empty dated string.
3. Class and target names use lower-case stable identifiers.
4. Every class value has only the known optional setting `effort`; `inherit` carries none, and each other current class carries one value from the closed schema vocabulary `low`, `medium`, or `high`.
5. Target keys must match implemented adapters; the current set is exactly `copilot`. Every target has exactly `emits` and `models`. A future target is accepted only with its production renderer, not by a dormant config row.
6. `emits` is a unique list containing only `model` or `effort`.
7. Every target model map covers exactly the declared class keys. `inherit` maps to `null`; current pinned classes map to non-empty strings.
8. Unknown fields, unknown setting names, extra or missing class coverage, empty values, and malformed JSON identify the offending target, class, or setting and throw before any partial object is exported.

The validator deep-freezes the parsed data. It has no default models, environment merge, project/user overlay, runtime discovery, schema package, or settings service. Effort is validated but `resolveCopilotModel` does not return it because the only production adapter does not emit it. A future adapter adds its own renderer and resolver when it gains a caller; adding its config target is a new key, not a loader redesign.

Caller paths are explicit:

| Caller | Configuration argument |
|---|---|
| `scripts/build-dev.mjs`, `scripts/build-release.mjs` | Absolute `src/config/agent-models.json` path |
| Installed compose add/verify, Dude lint, and pack scaffolding | Absolute `.github/skills/dude-engine/config/agent-models.json` path under the selected bundle root |
| Compose remove/list/status | None; these paths do not import or evaluate the loader or renderer |

Both builds retain the canonical bytes separately from the frozen parsed object, validate before cleanup, output staging, or writes, and copy those bytes unchanged to `.github/skills/dude-engine/config/agent-models.json`. That destination is already ordinary content below the upgrade-owned `.github/skills/dude-engine/` root. Do not add `.github/config`, a config-specific ownership rule, or another root preflight.

### 2. Neutral parser and one Copilot renderer

Keep these responsibilities in `src/skills/dude-engine/lib/agent-projection.mjs`:

```text
parseAgentSource(bytes, { stem, config }) -> { stem, frontmatter, body }
validateAgentSet(records)
copilotAgentPath(stem) -> ".github/agents/<stem>.agent.md"
renderCopilotAgent(record, config) -> Buffer
```

`parseAgentSource` keeps the corrected frontmatter behavior: leading canonical block only, comments allowed, current source keys only, named diagnostics, no concrete `model`, `effort`, or `reasoningEffort`, and no speculative key. It validates `model-class` against the passed configuration and source tools against the currently used Copilot selectors: `read`, `edit`, `search`, `execute`, `todo`, `agent`, `workiq/*`, and `workiq2/*`. The Copilot renderer preserves those selectors rather than translating through a multi-host tool table.

`renderCopilotAgent` emits `name`, `description`, `tools`, optional `agents`, optional `user-invocable`, optional `argument-hint`, and the model returned by `resolveCopilotModel(config, modelClass)`; `inherit` omits model. It preserves the body and never emits `model-class` or effort. It imports no configuration bytes and receives the frozen object explicitly.

Delete `PROJECTION_TARGETS`, plural projection path/output APIs, the executable three-target support matrix, `renderClaude`, `renderSdk`, Claude/SDK tool spellings, SDK wrapper fields, SDK effort evidence, and every Claude/SDK test. The adapter contract moves the useful field correspondence into developer documentation. There is no renderer registry for one renderer.

`validateAgentSet` treats `agents` itself as the composite declaration. Omission means leaf. Presence requires a non-empty roster of unique stable stems, with no display name or self-reference, all resolving in the supplied complete set. `agents: ["*"]` is valid only for the `dude` stem and cannot mix with explicit stems. Core builds pass the complete core set; compose passes the complete incoming set for one pack before staging. There is no `composite` key, registry, cycle framework, or repository-wide cross-pack claim. Existing destination ownership still rejects a stable-stem collision with core or an installed pack.

Apply one bounded source correction at `library/packs/technical-docs/agents/dude-pack-technical-docs-writer.agent.md`. Add only this missing roster:

```yaml
agents: ["dude-pack-technical-docs-extractor", "dude-pack-technical-docs-planner", "dude-pack-technical-docs-drafter", "dude-pack-technical-docs-reviewer"]
```

Keep the existing `agent` tool and body unchanged. The roster makes the writer's existing four-subagent orchestration explicit; it does not add a metadata key, cycle framework, or broader Technical Docs pack redesign.
